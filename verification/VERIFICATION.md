# 구매 요청에 따른 독립 검증

**최종 수정본은 Python 3.10.21과 3.12.3에서 각각 17개 시나리오를 모두 통과했다.** 실제 고객 파일을 받은 것은 아니며, 모든 입력은 독립 검증 담당자가 만든 합성 자료다. 발주자가 결과를 사용·수용·결제했다는 뜻은 아니다.

검증 기준은 [현재 공개 모집 중인 CSV 검증 의뢰](https://www.freelancer.com/projects/bash/CSV-Data-Validation-Maintenance)의 배포 전 검증, 오류 위치 보고, CLI·CI 사용, 원본 보존 요구에서 도출했다. 제작자의 내부 함수를 호출하지 않고 별도 프로세스에서 납품 CLI를 실행하고 보고서를 읽었다.

## 최종 결과와 확인 범위

| 시나리오 | 확인한 동작 |
|---|---|
| 정상 CSV 여러 개 | 오류 없음, 보고서 헤더만 생성, 종료 코드 0. UTF-8 BOM과 다른 헤더 순서도 처리 |
| 오류가 섞인 여러 파일 | 누락·정규식 형식·허용하지 않는 문자·줄바꿈·파일 간 중복의 7개 발견 항목과 위치가 정확히 일치 |
| Markdown 보고서 | CSV와 동일한 7개 항목의 파일·논리 행·열·열 번호·물리 시작/종료 줄·오류 코드 보존 |
| 복합 중복 키 | 같은 ID·다른 이름은 허용, ID·이름이 모두 같은 다음 파일 행은 중복으로 보고 |
| 헤더 오류 | 누락·중복·예상하지 않은 헤더를 헤더 위치로 보고 |
| 열 수가 다른 행 | 짧은 행과 긴 행 모두 오류로 위치 표시 |
| 완전히 빈 파일 | `empty_file`, 논리 행 0, 종료 코드 1 |
| 헤더만 있는 파일 | `no_data`, 종료 코드 1 |
| 닫히지 않은 CSV 따옴표 | `csv_syntax`, 종료 코드 1 |
| 세미콜론 설정 | 쉼표를 가정하지 않고 지정한 구분자로 정상 처리 |
| 없는 입력 파일 | 설명을 stderr에 쓰고 종료 코드 2 |
| 잘못된 JSON 설정 | 처리되지 않은 traceback 없이 설명과 종료 코드 2 |
| 잘못된 정규식 설정 | 설명과 종료 코드 2 |
| 기존 보고서와 입력 읽기 실패 | 보고서 원래 바이트를 보존하고 종료 코드 2 |
| 기존 일반 보고서의 정상 갱신 | 정상 실행 후 새 보고서로 교체 |
| 입력 CSV를 보고서 경로로 지정 | 원본을 덮어쓰지 않고 종료 코드 2 |
| 규칙 JSON을 보고서 경로로 지정 | 설정을 덮어쓰지 않고 종료 코드 2 |

각 실행 전에 입력 CSV와 설정 파일의 SHA-256을 구하고 실행 후 다시 비교했다. 오류가 있는 입력도 변경되지 않았다. 여러 줄 필드의 오류는 **논리 행 6, 물리 줄 6–7**로 구분해 표시됐다. 오류 위치를 검증할 때 구현의 검사 함수나 출력 생성기를 재사용하지 않았다.

## 최종 소스와 실행 근거

- 검증한 CLI: `csv_validate.py`.
- 최종 SHA-256: `f147a84ccbe4aff2b6c85d50b9fb5f1c9e6bd1f116174a60754a51cc82907205`.
- [Python 3.10 최종 실행 JSON](final-python310.json): 17건 통과, 0건 실패.
- [Python 3.12 최종 실행 JSON](final-python312.json): 17건 통과, 0건 실패.
- 실제 입력·보고서·실행 인수·stdout/stderr·입력 전후 지문은 각각 `final-python310/`, `final-python312/`와 위 JSON에 보존했다.
- 앞서 실행한 `python310.json`, `python312.json`은 제작자의 짧은 행 처리 보완 전 소스 기록이며 **최종 수용 근거는 `final-` 파일**이다.

각 JSON에 실제 시작·종료 UTC와 계측 시간이 있다. 실행 시간은 작은 검증 묶음의 소요 시간이며 고객 업무의 시간 절약이나 처리량 측정치가 아니다. 소스는 독립 검증 담당자가 수정하지 않았다.

## 다시 실행하기

결과물 폴더 `deliverables/csv-validation-service`에서 다음을 실행한다. 산출물 폴더는 기존에 없는 경로여야 한다.

```bash
python3 verification/verify_cli.py \
  --cli csv_validate.py \
  --artifacts verification/new-run \
  --report verification/new-run.json
```

다른 설치된 인터프리터로 CLI를 검사하려면 `--python /path/to/python3.10`을 추가한다. 검증 도구와 납품 CLI는 표준 라이브러리를 사용한다. 새 환경에서 다른 버전의 Python을 받기 위한 별도 도구가 필수인 것은 아니다.

## 실제 실행 환경과 한계

호스트는 **Ubuntu 24.04.1 LTS / Linux x86-64 / WSL2**다. 시스템 Python 3.12.3과 `uv`로 받은 Python 3.10.21을 실제로 실행했다. **Ubuntu 22.04 자체에서 실행한 것은 아니다.** 이 환경의 Docker는 WSL 통합이 없어 사용할 수 없었고 호스트 설정은 변경하지 않았다. 고객이 요구한 정확한 OS의 최종 수용은 Ubuntu 22.04 CI 또는 고객 환경에서 추가 확인해야 한다.

실제 고객의 규칙과 파일은 미확보다. 고객별 허용 문자·형식·중복 범위를 합의하기 전까지 예제 설정을 정답으로 제시하지 않는다. 큰 파일 처리량·메모리 상한, 고객 CI 연결, 심볼릭 링크·하드 링크의 모든 조합, 비정상 파일시스템·중단 시나리오는 이번 17건의 검증 범위 밖이다. 입력 파일을 수정하거나 정리하는 기능은 시험·제공 범위에 넣지 않았다.

## 유료 수요 증거와 상업 상태

[공식 API 최소 증거](evidence/paid-demand.json)에는 선택한 발주의 시간제 INR 750–1,250 예산, `active` / `open`, 공개 첨부 미확보와 조회 시각이 있다. 가격이 공개됐다는 것과 자금이 확보된 계약은 다르다. 사용자 운영자의 계정·제안 발송·고객 수용·대금은 검증하지 않았다.

관련 조사: `commercial/paid-demand-verifier.md`. 발주 플랫폼에서 만난 고객을 외부 PayPal 결제로 옮기는 방법은 이 검증이나 제안에 포함하지 않는다. 사용자의 PayPal 보유는 별도의 직접 거래에서 합의 가능한 수취 수단이라는 정보이며 현재 발주의 수주·수금을 증명하지 않는다.
